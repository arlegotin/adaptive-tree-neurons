# Managed data-preparation execution: implementation contract

The existing prepared-data reader authenticates recorded source and raw/sealed
byte bindings. It does not independently authenticate the preparation process or
its runtime. The remaining qualification registry needs that additional evidence
before treating a native fit as trained on the actual official acquisition.

`research.preparation_execution_v2.run_managed_preparation` now runs the existing
six-table preparation in an owned worker with the qualified core interpreter and
locked data overlay. It retains configuration/acquisition/raw/source/runtime
commitments, process and resource receipts, and immutable sealed outputs.
`load_preparation_execution(reference)` reopens those commitments without
decoding role archives, rerunning preparation or fitting models.

The worker checks the 27 core distribution identities and three pinned data
distributions. Every declared private file and locked wheel RECORD is checked;
selected actual core/data import files are joined to those RECORDs. It verifies
the exact Python/platform and before/after source, locks and inputs. The reader
joins these captured imports, process invocation and suite command/environment,
all six schemas/counts, 180 role archives and 30 opaque protected-label archives.
Owned RSS samples are recomputed; the process has no wall-time cap. Measurements
cover the root worker rather than an aggregate of all processes.

Data preparation necessarily parses raw target columns to create and seal roles.
It computes no model or protected metric. Model-development workers retain their
F/G/V boundaries; the proof reader hashes protected archives as opaque bytes.
Managed generation evidence and independent numerical data reconstruction are
separate claims. Native training, practical model eligibility and protected
inference remain subject to the complete qualification registry and protocol.

The original archived-commit byte/source audit retains its behavior and false
execution/runtime claims. The separately named current-source opaque audit
supplies byte/schema checks to this managed proof. Earlier prepared suites and
native models are not migrated to the new source.

Implementation verification passed 57 preparation/data/process checks, including
an actual six-table run on copies of the retained official raw assets. The reader
was forbidden to call NumPy archive loading or preparation. Consistently
recommitted wrong import hashes, model counts, RSS counts, protected bytes,
schema/authority flags and suite commands are rejected; controlled mutations
restore the original fixture inventory. This suite is separate from the earlier
57 native-workload checks, and neither is a whole-repository pass.

The data overlay contains byte-verified copies of the same 227 locked files,
without installing or updating packages. Generated bytecode was excluded. An
inherited zero-byte package-manager marker initially failed the exact inventory;
it was retained outside the import overlay. The [component receipt](WP07-managed-preparation-execution-receipt.json)
records that failure, all reader gaps found before correction and final evidence.
The fixture outputs are not the final production prepared suite. Complete
registry/production/protected qualification remains pending.
