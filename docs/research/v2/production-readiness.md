# Final practical source readiness

Readiness binds the committed scientific package, actual native qualification,
fixed production fixtures and a fresh whole-branch review. It is separate from
predictive success and is not permission to open protected data. Actual complete
native qualification under the final source and a completed review are still
required; no genuine readiness seal or protected outcome exists yet.

`production_readiness_v2.seal_production_readiness` and
`load_production_readiness` reopen the **actual native registry first**, before
reading caller-provided review, software or source references. The existing
registry independently checks its seven native implementation profiles, all 120
anchors, 258 support qualifications, recovery and official prepared-data evidence.
No caller Boolean or persistent cached success replaces those checks. Within a
single real public validation call, a private context may retain the immutable
JSON returned by the actual native/global loaders. Nested searches reuse those
prerequisites; source guards, checks of each selected search/model, and complete
retained-input guards at the end remain required. The context is discarded at
return or failure. It cannot be supplied through a public function argument.
Immutable publications finish the retained-input guards before writing output.

The separate `production_verification_v2` profiles exercise the practical search,
protection, pipeline and reporting contracts. They use the existing process
supervisor with one-thread fresh workers, a default4GiB root-RSS guard and no
wall-time cutoff. Their request binds all current source/test/lock identities;
the read-only loader checks the supervised command, environment, interpreter,
closed process, immutable log inventory and JUnit. Every fixed input test file
must contribute cases. Failed, skipped, duplicate, empty or unrelated cases
cannot supply a successful profile. A supplied green JUnit document alone is
not qualification. These profiles grant software evidence only: no native-model,
predictive-quality or protected-access authority.

The scientific package uses the existing `protocol.execution_snapshot`:
`pinned_commit`, `checkout_commit`, the exact execution-file map and its
`execution_sha256`. Git, index and working bytes must agree; untracked execution
overrides fail. A later documentation-only commit may change the checkout ID
while preserving the same pinned scientific files and digest. Reports use the
pinned commit and execution digest, retaining the core-source hash separately.

The review JSON has this exact metadata contract:

| Field | Required meaning |
| --- | --- |
| `schema` | `research/v2-production-branch-review` |
| `reviewed_commit` | Full commit actually inspected by the fresh reviewer |
| `final_commit` | Final committed scientific revision |
| `final_execution_sha256` / `source_sha256` | Actual final package/core identities |
| `review_package_reference` / `review_response_reference` | Exact durable file commitments, outside disposable skill scratch |
| `reviewer` | Recorded `agent_id`, `model`, `reasoning_effort` |
| `findings` | Complete material dispositions and deferred minors |

Each finding contains `finding_id`, final `severity`, `resolution`,
`changed_files`, `red_reference` and `green_reference`. Important/Critical
findings must be fixed with retained RED/GREEN evidence. Deferred minors retain
their IDs and make no scientific changes. The actual Git delta from reviewed
to final commit must equal the union of the documented fixed execution files;
unreviewed extra source changes block readiness. This represents the skill's
single fix pass honestly; it does not pretend the reviewer read the later fixes.
Review provenance remains an auditable operator record, not cryptographic
authentication of a person's identity. It cannot replace the actual native,
source or software checks.

The CLI accepts `production_verification` through `run`, and `readiness` through
`run` or `freeze`, using the strict control schema in
[practical-cli.md](practical-cli.md). A verification control takes `profile`,
the absolute qualified `interpreter`, optional project `extra_pythonpath` and
an optional operational `rss_limit_bytes`. Profiles are fixed in source; callers
cannot select new test files. A readiness control takes
`qualification_reference`, all four `verification_references`,
`review_reference` and the full `pinned_commit`. Its output is a fresh JSON file
outside all protected source/runtime/data/proof inputs, for example under
`artifacts/research-v2/readiness/`. Plan receipts carry no authority.

Readiness publication and loading rebuild the complete binding and recheck
source consistency. Historical receipt bytes and results keep their original
identities. A code/lock/test change requires new affected proof identities;
there is no silent migration of old native fits into the new revision.

The metadata tests deliberately use inert artificial review/source identities
and reject fake native gates. They do not produce a positive native/readiness
mock. Actual supervised fixture execution and its counts are recorded separately
from these supplied-metadata checks. The historical whole-suite failures and
current legacy memory-pressure setup errors remain disclosed; a scoped fixture
profile does not relabel them a monolithic green run.
